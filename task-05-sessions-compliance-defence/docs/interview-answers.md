## On Sessions

**1. What should a secure browser session look like? Name every property and what each one prevents.**
A secure browser session relies on a cryptographically secure, random, opaque identifier (e.g., 32 bytes of entropy) generated on the server. This token is hashed before being stored in the database and sent to the client as a cookie. The cookie must have strict flags configured. The `HttpOnly` flag prevents client-side JavaScript from accessing the cookie, entirely mitigating cross-site scripting (XSS) token theft. The `Secure` flag ensures the cookie is only transmitted over encrypted HTTPS connections, preventing man-in-the-middle (MITM) packet sniffing. The `SameSite=Lax` or `Strict` flag prevents the browser from automatically attaching the cookie to cross-origin requests, effectively neutralizing cross-site request forgery (CSRF) attacks. Finally, an explicit `Max-Age` or `Expires` attribute limits the lifespan of the session, preventing stale tokens from existing indefinitely on idle devices. 

**2. What is session fixation, and what prevents it?**
Session fixation is an attack where an adversary forces a known, valid session identifier onto a victim's browser (e.g., via a crafted URL or an injected cookie). When the victim subsequently logs into the application, the server normally elevates the permissions associated with that existing identifier. Because the attacker already knows this token, they instantly gain authenticated access to the victim's account without needing their password. The definitive prevention for session fixation is strictly regenerating a brand-new session identifier upon any privilege escalation. When a user authenticates, the application must completely discard the anonymous or pre-auth session token and issue a fresh, secure token tied to the newly authenticated state.

**3. Are tokens better than server-side sessions? Answer for your own application, not in general.**
For NucleoBridge, database-backed server-side sessions are vastly superior to stateless JWT tokens. Our platform requires strict, immediate access revocation capabilities. For example, if an author alters a case study tier, if an admin initiates an account deletion, or if a user resets a compromised password, we must terminate existing sessions instantly. Stateless JWTs cannot be reliably invalidated before their expiration time unless you implement a server-side blacklist—which essentially recreates a database session but with more complexity and worse performance. Given our PostgreSQL and Prisma stack, looking up a hashed session token via an indexed database query is incredibly fast, and it provides absolute, centralized control over the security state of the platform.

**4. How would you implement log out of all devices?**
To implement a global logout across all devices, I leverage the relational structure of the database. When a user triggers this action, the server takes their authenticated `userId` and executes a Prisma query to delete all records in the `Session` table where the `userId` matches. Because the state is entirely centralized in PostgreSQL, this single transaction instantly invalidates every active token they have in existence. On the very next network request from any of their other devices, the server will read the cookie, hash it, query the database, find zero matching records, and immediately reject the request—clearing the client's cookie and routing them to the login screen.

**5. How do you invalidate existing sessions on a password change?**
Invalidating sessions upon a password change is critical for evicting potential attackers. I handle this by wrapping two operations in a single atomic Prisma `$transaction`. First, the system updates the `User` record with the newly generated Argon2id password hash. Second, it executes a `deleteMany` command against the `Session` table for that specific `userId`, wiping the slate clean. Crucially, the system does not automatically log the user in with the new password. The HTTP response clears the current device's cookie, forcing the user to navigate back to the login page and re-authenticate from scratch, proving they have the new credentials and ensuring complete zero-trust eviction.

**6. What do the HttpOnly, Secure and SameSite cookie flags protect against, and what does each one fail to protect against?**
`HttpOnly` protects against XSS attacks by preventing JavaScript from reading the session cookie. However, it fails to protect against CSRF, because the browser will still blindly attach the cookie to forged requests. `Secure` protects against network eavesdropping (MITM) by forcing transmission over HTTPS. However, it fails to protect against local device compromise; if malware is on the machine, it can read the encrypted cookie from the browser's storage. `SameSite=Lax/Strict` protects against CSRF by preventing the cookie from being sent on cross-site sub-requests. However, it fails to protect against XSS; if an attacker injects a script into your origin, that script can still make authenticated API calls directly from the trusted domain.

**7. What is the difference between a 401 and a 403, and how should the interface treat them differently?**
A 401 Unauthorized status means the server does not know who the user is—they are unauthenticated or their session has expired. The client interface should treat this by immediately redirecting the user to the login screen or rendering a credential prompt. A 403 Forbidden status means the server knows exactly who the user is, but they lack the necessary permissions to perform the action (e.g., a standard learner trying to access the NucleoBridge author dashboard). The interface should never redirect a 403 to the login screen, as they are already logged in. Instead, it should render an "Access Denied" page or elegantly hide the restricted UI elements.

## On your own session work

**8. Why must logout be handled on the server rather than the front end, and what exactly stays alive if it is not?**
Logout must be a server-side destructive action because the server is the ultimate source of truth for access. If you only handle logout on the front end—by using JavaScript to delete the local cookie and redirecting to the homepage—the session record itself remains perfectly valid and active in the database. If an attacker had previously intercepted that token, or if the user later restores their browser state, that token will still grant full authenticated access to the application. True logout requires the server to physically delete the session row in PostgreSQL, permanently severing the cryptographically valid link.

**9. What is the difference between authentication and authorisation, and which one does a protected route need?**
Authentication (AuthN) is the verification of identity—it asks, "Are you who you say you are?" We enforce this by checking Argon2id hashes and session tokens. Authorization (AuthZ) is the verification of permissions—it asks, "Are you allowed to do this?" We enforce this by checking the user's `role` (e.g., `USER` vs. `ADMIN`). A protected route, such as the case-study tier management interface, strictly requires both. It must first authenticate the session to know the identity, and then it must authorize that identity to ensure they hold the `ADMIN` role before granting access.

## On compliance

**10. A user asks you to delete their account. Walk me through what happens, from the request to the data being gone.**
When a user requests deletion via the API, the system immediately executes a soft-delete protocol. It sets a `deletionRequestedAt` timestamp to the current date and instantly deletes all active records in the `Session` table, logging them out globally. Their personally identifiable information (name, email) is anonymized with dummy data (e.g., `deleted-[uuid]@example.com`). This initiates a 30-day grace period. A daily scheduled background job queries PostgreSQL for accounts where `deletionRequestedAt` is older than 30 days. Using a Prisma transaction, this job cascade-deletes all non-financial child records (like document chunks) and completes the process.

**11. Which data would you refuse to delete on a deletion request, and on what basis?**
I would strictly refuse to delete any records in the `Payments` and `PaymentAttempts` tables, as well as the minimal, anonymized `User` stub required to maintain relational integrity for those transactions. The basis for this refusal is superseding legal and financial compliance. Anti-money laundering (AML) laws and national tax authorities mandate that businesses retain exact financial ledgers and transaction histories for statutory periods (often 5 to 7 years). A user's right to erasure under frameworks like GDPR is not absolute; it does not override a business's legal obligation to maintain accurate financial accounting. 

**12. What happens to your backups when a user is deleted?**
When a user is purged from the active production database, their historical data inevitably remains trapped within encrypted, immutable database snapshots and backups. Privacy laws generally accept that organizations do not have to immediately rewrite massive backup tapes, provided they are securely stored. However, to remain compliant, we must maintain a secure suppression logic. If a database backup from last month ever needs to be restored to production, the system must recognize that the user had previously requested deletion and instantly re-purge their data to prevent them from being accidentally resurrected.

**13. What is the difference between anonymising and deleting, and when is anonymising sufficient?**
Deleting means physically wiping the data row from the storage medium so it ceases to exist entirely. Anonymising means permanently and irreversibly scrambling personal identifiers (like changing an email to a random UUID) so that the data row still exists, but can no longer be tied back to a human being. Anonymising is sufficient—and heavily preferred—when the structural integrity of a relational database depends on that record. For example, to keep accurate financial ledgers in NucleoBridge, we must anonymise the user to break the identity link while retaining the structural row to prevent cascading deletion of their payment history.

## On the role

**14. Why do you want to work as a forward deployed engineer specifically, rather than as a software engineer?**
A traditional software engineer often works in isolation, building features against abstracted specifications and disconnected from the chaos of the end-user. I specifically want to be a forward-deployed engineer because the most complex engineering challenges are operational, not just technical. I want to build platforms like NucleoBridge directly against the raw realities of the client—in this case, bioinformatics researchers. An FDE bridges the gap between the codebase and the messy, real-world deployment environment, allowing me to solve actual business problems in real-time rather than building perfect code for hypothetical scenarios.

**15. A customer says they want to use AI to improve their operations. How do you respond?**
I respond by immediately shifting the conversation away from AI and asking: "What specific operational bottleneck are you actually trying to solve?" Customers frequently view AI as a magic wand for poorly defined business problems. If they want to help students dynamically navigate complex genomic case studies, a conversational LLM makes sense. But if they just want to see which cohorts finish fastest, a standard SQL dashboard is cheaper, faster, and more reliable. My job is to demystify the technology and map it strictly to return on investment (ROI); if AI isn't the best tool for their specific pain point, I advise against it.

**16. What is the difference between a RAG system and a fine-tuned model for an enterprise deployment?**
Fine-tuning permanently bakes new knowledge directly into a model's neural weights. It is highly expensive, slow to update, and prone to hallucination if the underlying facts change. RAG (Retrieval-Augmented Generation) keeps the model's weights completely frozen. Instead, it queries an external vector database (like PGVector) for relevant documents and injects them into the prompt at runtime. For an enterprise, RAG is vastly superior for factual workflows. It allows you to instantly update knowledge without retraining, strictly enforce role-based access control on individual documents, and trace every single AI answer back to a concrete, verifiable source.

**17. How do you evaluate whether an AI agent is working correctly in production?**
You cannot evaluate an AI agent on vibes; it requires deterministic, automated metrics. I evaluate it by building an evaluation pipeline (using frameworks like Ragas or TruLens) running against a "ground truth" dataset of historical queries. I measure three distinct axes: Retrieval accuracy (did the vector search return the correct case study?), Generation quality (did the LLM synthesize the retrieved context accurately without hallucinating external facts?), and Tool Execution success (did the agent trigger the correct backend functions with the right schema?). This pipeline runs in CI/CD to prevent regressions before deployment.

## On state management

**18. How do you decide between local component state, context, and an external state manager?**
I default to local component state (like React's `useState`) for ephemeral, UI-specific data that no other component cares about—such as a dropdown menu toggle or the text currently typed in a single input field. I use Context for low-frequency global data that rarely changes but needs to be accessed everywhere, like the current visual theme or the user's authentication status. I only reach for an external state manager (like Zustand) when the application hits the "prop drilling" ceiling—specifically when high-frequency, complex global state must be mutated and accessed across entirely separate branches of the application without triggering massive, crippling re-renders.

**19. How do you handle server state, as distinct from client state?**
Server state is the ultimate source of truth residing in the database (such as a user's role). It is fundamentally asynchronous and can become stale the moment it reaches the browser. Client state is ephemeral UI state existing only in memory (such as modal visibility or local form data). In a Next.js architecture, I handle them entirely differently. I use Server Components and data fetching libraries to act strictly as a synchronization layer for server state, keeping it rigidly isolated from the local client state to prevent data collisions and architectural complexity.

## On your own work

**20. Cite three specific numbers from your own tasks one to four: one from your type scale, one timing figure from your hashing comparison, and one from your rate limit configuration. Explain what each number means and why you chose it.**
1. **Type scale: 1.5 line-height ratio (Display Large: 64px / 96px).** I applied the same 1.5 multiplier across all 15 styles in my DM Sans scale—five roles, each with three sizes—because it gives the interface a consistent vertical rhythm while keeping headings readable on small screens. The 64px display size paired with a 96px line height prevents the largest text from feeling cramped or disproportionately massive beside body copy.
2. **Argon2id hashing time: 153.72ms.** In my hashing comparison, Argon2id took 153.72ms per hash while SHA-256 took 0.892ms, which works out to roughly 7 guesses per second versus roughly 1,121. I use the OWASP baseline configuration (19 MiB memory, timeCost 2, parallelism 1) because a delay in that range is imperceptible during a normal login but makes offline brute-force cracking economically expensive.
3. **Rate limit configuration: 5 requests per 15 minutes per IP.** I applied this to the authentication endpoints—sign-in, signup, and password reset—because five requests leaves a legitimate user room to mistype a password or email a few times, while a 15-minute window makes automated brute-force and credential-stuffing attempts impractical. The limiter is deliberately simple and in-memory for now; the primary defence against email enumeration is the uniform generic response and dummy Argon2 verification, not the rate limit itself.

**21. Across all five tasks, name the decision you are least confident about. Say what you would need to find out to settle it, and what you would do if the answer went against you.**
My least confident decision is combining traditional relational data and PGVector embeddings within the same single Neon PostgreSQL instance. While it simplifies the architecture now, I am uncertain at what specific row count the Exact Nearest Neighbor (KNN) vector math will begin to monopolize CPU resources and degrade standard relational queries. To settle this, I need to execute a load test with 100,000 dummy vector embeddings and monitor the `EXPLAIN ANALYZE` execution plans. If the performance drastically degrades the core API, I will decouple the architecture and migrate the embeddings to a dedicated external vector database like Pinecone.

### Additional Viva Preparation Notes (RAG & Vector Context)
* **RAG vs Fine-tuning:** Use RAG for dynamic, factual knowledge (e.g., retrieving records from the business's records); use fine-tuning for altering model tone or specific output formats.
* **Chunking:** Splitting documents into semantic blocks. Choose size based on context window limits and the typical length of a complete thought/answer in the source data.
* **Hallucination in RAG:** Models can still hallucinate if retrieved context is irrelevant or if the prompt doesn't strictly confine the model to the provided text. Reduce this with strict system prompts.
* **Retrieval vs Generation Failure:** Logs showing the correct document was fetched but a bad answer was returned indicate a generation failure. Logs showing irrelevant documents were fetched indicate a retrieval failure. 
* **PGVector vs Dedicated DB:** PGVector is great for unified infrastructure. A dedicated DB (Pinecone) is better when scaling to millions of embeddings where vector math chokes the primary relational database.
