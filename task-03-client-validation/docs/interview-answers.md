**1. Why is client-side validation not enough?**
Client-side validation executes within the user's browser, an environment inherently outside the application's control. Malicious actors can trivially bypass frontend checks by disabling JavaScript, intercepting network requests via proxies, or using command-line tools such as cURL to send HTTP payloads directly to the server endpoints. Consequently, client-side validation is strictly a user experience enhancement, designed to provide immediate, helpful feedback for honest mistakes and reduce unnecessary server load. It is not a security boundary. Relying on the browser to enforce business rules leaves the database vulnerable to malformed payloads and injection attacks. Security requires zero trust; every incoming request must be treated as hostile. The server must enforce comprehensive data validation and authorization independently, verifying every field in the payload before executing any logic.

**2. What security checks belong in the frontend, and what must the server enforce regardless?**
No true security boundaries belong exclusively in the frontend; the frontend handles user experience validation, while the server enforces actual security. The frontend should perform format validation, enforce string lengths, guide password complexity, and manage CSRF tokens or secure JWTs in HTTP-only cookies to help well-intentioned users submit correct data efficiently. However, the server must independently re-verify every single rule. The server is strictly responsible for authorization (verifying the user has permission to perform the action), authentication (verifying identity), business logic constraints, and data sanitization to prevent SQL injection and Cross-Site Scripting (XSS). Even if the frontend hides a restricted UI component, the backend must actively block unauthorized API calls to that resource. The frontend is a convenience layer; the server is the absolute source of truth.

**3. The user interface hides the delete button for non-administrators. Is that enough?**
Hiding the delete button for non-administrators is necessary for a clean user interface, but it is fundamentally insufficient for security. UI state manipulation operates entirely on the client side, meaning the underlying API endpoint handling the deletion remains exposed to the network. An attacker can use browser developer tools to inspect the network traffic, identify the target API route, and manually craft an HTTP request, bypassing the frontend completely. If the server does not explicitly verify the authorization level of the user making that request, it will execute the deletion regardless of whether the button was visible. Security requires robust server-side authorization. The endpoint must decode the user's session token, verify their role against the database, and confirm they have explicit administrative privileges for that specific resource before processing the operation. Visual concealment is not access control.

**4. What is the difference between validation, encoding and sanitisation?**

- Validation ensures that incoming data conforms to expected rules, types, and constraints before processing. It answers whether the data is in the correct format, such as confirming an input is an integer within a specific range, and rejects non-conforming data outright. 
- Sanitization involves modifying the incoming data to remove or neutralize potentially harmful content, such as stripping executable JavaScript from a user comment to prevent basic injection attacks. It attempts to clean bad data so it can be saved safely. 
- Encoding translates special characters into their safe, representational equivalents just before rendering them in the browser. Encoding prevents the browser from interpreting user-submitted strings as executable code, serving as the primary defense against Cross-Site Scripting (XSS). 
- In Summary, while validation dictates what enters the system, sanitization cleans it, and encoding dictates how it is safely displayed.

**5. Why should you validate route parameters and query strings, not just the body?**
Route parameters and query strings dictate critical application state, resource retrieval, and navigation logic. Because they are prominently displayed in the URL, they are the most accessible attack vector for manipulation. Attackers frequently modify URL parameters in an attempt to trigger Insecure Direct Object Reference (IDOR) vulnerabilities, accessing data belonging to other accounts. Furthermore, query strings are often injected directly into database queries for filtering and pagination. Failing to validate their type and constraints leaves the application vulnerable to injection attacks or application crashes caused by unexpected data types. Every input vector represents untrusted data crossing the system boundary. Thorough validation of the entire request ensures state mutations and data queries remain predictable, secure, and structurally sound.

**6. Explain what a single page application is, and how you make one discoverable by search engines.**
A Single Page Application (SPA) dynamically rewrites the current web page with new data from the server, rather than loading completely new pages on every interaction. This eliminates full page reloads, preserving client-side state and offering a fluid user experience. When a user navigates, JavaScript intercepts the event, updates the URL via the HTML5 History API, and fetches only the required JSON data to render the new view. To ensure search engine discoverability, SPAs must implement Server-Side Rendering (SSR) or Static Site Generation (SSG), often utilizing frameworks like Next.js. Because traditional web crawlers struggle to execute complex asynchronous JavaScript required to render client-side SPAs, SSR executes the React component tree on the server. This guarantees the crawler receives a fully populated, semantically structured HTML document on the initial request, complete with metadata and readable content.

**7. What are the advantages and disadvantages of a single page application against a multi-page application?**
The primary advantage of an SPA is the seamless, instantaneous user experience. By fetching only JSON payloads rather than full HTML documents on navigation, SPAs minimize bandwidth consumption and eliminate jarring page reloads. This persistent state allows for complex interactive features like uninterrupted background audio or intricate multi-step forms. The drawbacks include larger initial payload sizes, as the browser must download the foundational JavaScript bundle before rendering interactivity. SPAs also demand robust client-side routing to properly handle browser history. Conversely, Multi-Page Applications (MPAs) excel in initial load speeds for static content, as the server delivers ready-to-render HTML. They offer flawless out-of-the-box SEO and require less client-side processing power. However, MPAs suffer from latency during navigation, as the browser must tear down and rebuild the entire DOM, making them less suitable for highly interactive interfaces.

**8. Can you explain the four principles of the Web Content Accessibility Guidelines, with examples from your own work?**
The WCAG principles dictate that content must be Perceivable, Operable, Understandable, and Robust (POUR). Perceivable means information cannot be invisible to all a user's senses. In my authentication flow, I added a caution SVG icon alongside red error text, ensuring the error state is perceivable to users with color blindness. Operable requires that the interface cannot demand interactions a user cannot perform. I resolved a tab-sequence failure by applying `aria-disabled="true"` to the submit button, ensuring the form remains fully reachable via keyboard navigation. Understandable demands that users comprehend the information and operation. I implemented dynamic `aria-describedby` links on the password field, ensuring screen readers clearly articulate the minimum character constraints. Robust means content must be interpreted reliably by diverse assistive technologies. I applied semantic HTML and standard ARIA attributes guaranteeing the form scales reliably across different screen readers and browsers.

**9. Discuss the importance of semantic HTML in the context of accessibility.**
Semantic HTML is the foundational architecture of web accessibility. It utilizes explicit HTML tags that carry intrinsic meaning, rather than relying on generic, non-semantic containers. This structure directly informs the Accessibility Tree, which is the API that assistive technologies rely on to interpret the page. When a developer uses a genuine button element, the browser automatically provides critical built-in functionality: it becomes focusable via the keyboard, activates on the Space or Enter keys, and is announced specifically as an interactive control to screen reader users. Attempting to recreate this functionality on a generic division tag using JavaScript and ARIA attributes is error-prone and brittle. Semantic HTML guarantees that the underlying structure and purpose of the content are programmatically determinable, ensuring all users can navigate, comprehend, and interact with the application consistently.

**10. Tell me about a time when you disagreed with what a customer wanted to build.**
While developing the authentication flow for NucleoBridge, stakeholders I consulted suggested a strict automated system that would permanently lock an account after three failed One-Time Password (OTP) attempts to maximize security against brute-force attacks. However, I disagreed with this zero-tolerance approach. Because I had intentionally removed the "6-digit" length hint to prevent enumeration, legitimate users were slightly more likely to make formatting mistakes. Furthermore, standard email delivery delays often cause users to accidentally input expired codes. An automated permanent lockout would severely disrupt students and researchers, damaging trust and generating massive support overhead. I advocated for a progressive friction architecture instead. We compromised by building a system that implements a temporary 15-minute cooldown after successive failures, while instantly flagging the account for manual review if the attempts originated from anomalous IP addresses. This approach respected the goal of rapid threat mitigation while ensuring high-stakes lockout decisions remained guided by contextual judgment, drastically reducing critical friction for genuine users.

**11. How would you explain to a non-technical executive why their AI implementation is not performing as expected?**
I frame AI performance issues around data quality and context limits rather than algorithmic complexity. Drawing from my work on NucleoBridge, where users navigate complex, interactive bioinformatics steps, I explain that AI models are not reasoning engines; they are pattern-matching engines. If an AI assistant on the platform gives a user generic or incorrect guidance for their sequence analysis case study, it is usually because the context we are feeding it is incomplete. I compare it to hiring a brilliant biology consultant but locking them in a room with outdated textbooks and hiding the user's actual lab results. To improve the model's accuracy, we must bridge this context gap. For NucleoBridge, this involves refining our system prompts, implementing vector databases to retrieve the exact state of the user's bioinformatics pipeline, and injecting relevant, up-to-date documentation before querying the model. The AI can only provide highly accurate, specialized insights if our foundational data architecture delivers the right context at the exact moment of the request. 

**12. One of your validation rules wrongly blocks a category of legitimate user. Name the rule, name the users, and defend the trade-off or say you got it wrong.**
The enforcement of mandatory, separate "First Name" and "Last Name" fields on the NucleoBridge registration form wrongly blocks users from cultures where mononyms are common and legally recognized. By mandating two distinct name tokens to neatly fit Western naming conventions and our database schema, the rule actively prevents a legitimate global demographic (such as researchers from parts of Indonesia or South India) from registering without falsifying their identity. I got this wrong. While splitting names into two fields is convenient for automated email greetings and standardizing data, forcing a mononymous user to enter a placeholder like a period or repeat their name corrupts the data integrity we were attempting to protect. It creates a hostile user experience for a bioinformatics platform meant to have an inclusive, global reach. A superior technical solution would involve utilizing a single "Full Name" field to preserve the user's authentic identity, alongside an optional "Preferred Name" field for communications. The current rule prioritized developer convenience and legacy database structures over inclusive design.

**13. You sent a request directly to your own endpoint. Say exactly what happened and what it tells you about the eight rules you spent two days writing.**
I bypassed the frontend entirely using cURL, sending an HTTP POST request to the API endpoint with an intentionally malformed payload: a single-character name, a blank password, an unchecked terms boolean, and an invalid email format. The server rejected the request specifically because of the invalid email, returning an email-specific error message. While the email block succeeded, this experiment proves my frontend validation is merely a UX layer, not a security perimeter. The server only caught the email because that specific rule was duplicated backend. The other seven rules—password complexity, length, and terms acceptance—were never evaluated before the block. Relying on client-side JavaScript for data integrity leaves the database exposed to targeted API manipulation. Every client rule must be explicitly recreated server-side.

**14. Wrong-answer analysis. A candidate says: "I use strong client-side validation with regex on every field, disable the submit button until everything is valid, and sanitise all inputs in the browser before sending them. That covers the main injection and bad-data risks." This is confident and substantially wrong. Say which parts are useless, which are actively misleading, and what the candidate has confused with what.**

The candidate’s statement is deeply flawed and conflates UX with security. First, relying on strong client-side validation and disabling the submit button is entirely useless against malicious actors, as client-side restrictions are easily bypassed using intercepting proxies or direct API calls. Second, sanitizing all inputs in the browser is actively misleading; browser-based sanitization provides a false sense of security because the raw payload can be intercepted and modified post-sanitization before reaching the server. Finally, the candidate has confused the boundary of defense. They believe data cleanliness verified in the browser protects the database from injection risks. In reality, injection defense and sanitization must occur exclusively on the backend, immediately before execution. The frontend provides immediate user feedback; the server provides actual security.

**15. What is user enumeration, and how do error messages contribute to it?**
User enumeration is a cybersecurity vulnerability where an attacker exploits an application's responses to confirm whether a specific username or email address exists in the system's database. This allows attackers to harvest valid target lists for credential stuffing, brute-force attacks, or spear-phishing campaigns. Error messages are the primary conduit for this vulnerability. If a login form returns "Incorrect password" for a valid email, but "User not found" for an invalid one, the application explicitly leaks the account's existence. Similarly, a registration form that states "Email already in use" directly enumerates the database. To mitigate this, error messages must be uniform and ambiguous regardless of the backend state. A login failure should always return "Invalid credentials," completely obscuring the internal database state from the attacker.
