# docs/interview-answers.md

**1. What is the difference between Git Flow and trunk-based development, and why have a lot of teams moved toward trunk-based?**
Git Flow relies on multiple long-lived branches (such as `develop`, `release`, and `feature` branches), requiring developers to work in isolation for extended periods before executing massive, highly complex merges. Trunk-based development inverts this by having all developers integrate their work into a single shared branch (the "trunk" or `main`) multiple times a day using short-lived feature branches. Teams have aggressively moved toward trunk-based development because it perfectly complements Continuous Integration and Continuous Deployment (CI/CD) pipelines. By integrating constantly in small, manageable chunks, teams avoid "merge hell"—the painful process of resolving deep, conflicting changes that naturally occur when branches drift too far apart. Trunk-based development forces immediate conflict resolution, ensures the main branch is always in a deployable state, and radically reduces the feedback loop between writing code and testing it in a production-like environment.

**2. What does `git push --force` actually do, and why is `--force-with-lease` generally safer?**
`git push --force` blindly overwrites the remote branch with your local branch's history, regardless of what currently exists on the remote. If a colleague has pushed new commits to that remote branch since your last pull, a standard `--force` will permanently erase their work without warning. It essentially tells Git, "Make the remote look exactly like my local machine, no matter what." `--force-with-lease` acts as a crucial safety valve. Before overwriting the remote, it checks if the remote branch has been updated by someone else since you last fetched it. If the remote has new, un-fetched commits, `--force-with-lease` will reject the push, preventing you from accidentally destroying your teammate's code. This allows you to safely overwrite history (like after a rebase) while guaranteeing you are only overwriting your own known state.

**3. Why is rewriting history, through rebase, amend, or force push, dangerous on a shared branch?**
Git tracks commits using cryptographic SHA-1 hashes based on the commit's content, author, and parent commit. When you rewrite history using rebase or amend, you do not just move commits; you destroy the original commits and create entirely new ones with different hashes. If you do this on a shared branch (like `main`), the remote history will completely diverge from the local history of every other developer on your team. When those developers attempt to pull or push, Git will not recognize the new history. It will attempt to merge the old history with the new rewritten history, resulting in duplicate commits, catastrophic merge conflicts, and massive confusion. Rewriting history should be strictly confined to local, private feature branches before they are merged.

**4. What is the difference between `git merge` and `git rebase`, and when would you actually pick one over the other?**
Both commands integrate changes from one branch into another, but they handle the commit history differently. `git merge` is non-destructive; it takes the two branch endpoints and creates a new "merge commit" that ties their histories together, preserving the exact chronological sequence of every commit. `git rebase` is destructive; it rewrites history by moving the base of your feature branch to the tip of the target branch, reapplying your commits one by one. This creates a clean, linear history without merge commits. I pick `rebase` when updating a private, local feature branch with the latest changes from `main` to keep my commit history clean and readable. I pick `merge` when combining a finished feature branch into a shared `main` branch, as it accurately preserves the historical context of when and how the feature was developed.

**5. What causes a merge conflict, and what is actually happening in the file when you see the conflict markers?**
A merge conflict occurs when Git cannot automatically reconcile differences between two commits. This typically happens when two developers modify the exact same line in a file, or when one developer modifies a file that another developer has deleted. When Git encounters this, it halts the merge process and marks the file as conflicted. Inside the file, Git literally injects conflict markers: `<<<<<<< HEAD` (indicating the start of your current local changes), `=======` (the divider between the two versions), and `>>>>>>> [branch-name]` (indicating the incoming changes). The file is mathematically broken at this stage. You must manually open the file, decide which code to keep (or write a hybrid of both), delete the conflict markers entirely, and then save and commit the resolved file.

**6. What is the difference between the working directory, the staging area, and the repository?**
These represent the three primary states of a file in Git. The working directory is your physical file system; it contains the current, modified files you are actively editing on your disk (untracked and modified files). The staging area (or index) is a conceptual preparation zone; when you run `git add`, you are taking a snapshot of a file from the working directory and placing it in the staging area to build your next commit. The repository (the `.git` directory) is the immutable database of your project's history; when you run `git commit`, the files in the staging area are permanently stored in the repository as a new commit with a unique hash.

**7. What is branch protection, and what does it typically enforce?**
Branch protection is a set of administrative rules enforced by hosting platforms like GitHub to prevent destructive actions on critical branches (usually `main` or `production`). Because shared branches are the source of truth, they must be guarded against accidental breakage. Branch protection typically enforces that no one can push code directly to the branch; all changes must come through a Pull Request. Furthermore, it often requires at least one peer review approval, mandates that all automated CI/CD tests pass before merging, and strictly disables force pushes and branch deletion. This guarantees that only reviewed, tested, and verifiable code reaches the production timeline.

**8. Walk me through a technical project you built end to end.**

**9. Tell me about a time when something you built broke in production.**
During the deployment of a genomics analytics application, a crucial environment variable connecting the application to the production database was misconfigured. Because the frontend utilized an optimistic UI pattern, it did not strictly await a successful `201 Created` HTTP response from the backend before updating the state. When a user submitted a complex data payload, the interface displayed a success banner and routed them to the dashboard. However, under the hood, the Prisma client threw a `P1001` connection error because it could not reach the database. The data was entirely lost, resulting in a false success state. To fix this, I immediately rolled back, implemented strict error boundary handling on the API routes to catch `500` level errors, and tied the frontend state strictly to verified database responses rather than optimistic assumptions.

**10. How do you approach learning a new technical platform or codebase quickly when starting a new engagement?**
I rely on an empirical, first-principles approach, focusing on data flow rather than memorizing syntax. I start by mapping the foundational architecture: I examine the database schema (e.g., the `schema.prisma` file) to understand the core entities and their relationships. Once I understand the data shape, I identify the system's entry points (API routes, primary rendering components) and trace a single user request from the UI, through the controller logic, down to the database mutation, and back up. I concurrently review the `package.json` and CI/CD configurations to understand the build and deployment pipeline. By anchoring my understanding in how data is structured and mutated, the surrounding business logic and framework-specific quirks become much easier to contextualize and debug.

**11. What is the difference between code that is correct and code that is complete?**
Correct code solves the immediate mathematical or logical problem on the "happy path." It compiles, it executes the expected function, and it passes basic unit tests when provided with perfect inputs. Complete code is built for the hostile environment of production. Complete code anticipates failure. It includes robust error handling for network drops, invalid inputs, and unavailable databases. It features structured logging for observability, adheres strictly to the project's design system (using semantic tokens rather than hardcoded values), and is thoroughly documented. Correct code proves a concept works on a local machine; complete code ensures the feature can be safely maintained, scaled, and debugged by a distributed team over years.

**12. How do you design software for a customer who will need to maintain it after you are gone?**
Maintainability is about reducing cognitive load. I design with strict structural consistency and heavily favor established, boring technology over clever, obscure hacks. I enforce centralized configurations—such as using a single `main-tokens.css` file for all design variables—so global changes require editing only one file. I rely on strictly typed systems and ORMs like Prisma, which provide self-documenting schemas and safe database migrations. I ensure every architectural decision (why a specific model was chosen, why a specific API pattern was used) is documented directly in the repository via markdown files. Ultimately, I build the system so that a new developer can read the schema, trace the API routes, and deploy a minor update on their first day without fearing cascading failures.

**13. Your first page load took a specific number of milliseconds. Where did that time go? Name the parts you can measure and the parts you are guessing about.**
My first page load took 19,815 milliseconds. I can explicitly measure the Just-In-Time (JIT) compilation phase: the terminal logs confirm that 18.2 seconds (18,200ms) of that time was spent by Next.js compiling 470 modules for the root route. I can also measure the final HTTP response time. The remaining ~1.6 seconds are unlogged overhead. I am guessing this time was consumed by Node.js process initialization, establishing the initial Prisma connection pool to PostgreSQL 18, and file system read latency as the local development server spun up the underlying Antigravity environment. In a production build, the 18.2-second compilation phase is entirely eliminated via ahead-of-time building, drastically reducing the load time to standard network latency.

**14. Your application reported success to the user while writing nothing to the database. Explain the mechanism that allowed that, and name the one check that would have caught it in thirty seconds.**
This failure was allowed by an "optimistic UI" implementation lacking a strict error boundary. The frontend form was programmed to transition to a success state immediately upon the user clicking "Submit," assuming the backend write would naturally succeed. Meanwhile, the backend API route encountered a `P1001` database connection error (due to a missing `DATABASE_URL` environment variable) and silently failed, returning a 500 error that the frontend ignored. The one check that would have caught this instantly is inspecting the terminal or browser network tab for the precise HTTP status code. If there is no explicit `201 Created` status returned by the POST request, the database write did not happen, regardless of what the user interface displays.

**15. Wrong-answer analysis. A candidate says: "I always check my app is working by signing up a test user and confirming I get taken to the dashboard. If the dashboard loads, the backend is working." Say what is wrong with this, what it would miss, and what you would do instead.**
This answer fundamentally misunderstands the decoupling of frontend routing from backend persistence. The dashboard loading only proves that the client-side router and optimistic state management are functioning. It completely misses critical backend failures, such as a dead database connection, a failed password hashing function, or a broken SMTP email trigger. The user might be routed to a dashboard populated entirely by volatile client-side cache, while zero data is persisted. Instead of trusting the interface, I would submit the form and immediately check the server logs to verify a `201 Created` HTTP response. I would then directly query the database (e.g., using a diagnostic endpoint or Prisma Studio) to physically verify that the new user record, with the correctly hashed password, exists in PostgreSQL.

**16. Viva Preparation: How to handle accidentally committing sensitive information to a public repository.**
If I committed an API key, database password, or sensitive patient data to a public repository, the immediate assumption must be that the secret is already compromised. I would not attempt to just push a new commit deleting the text, as the secret remains permanently visible in the Git history. First, I would immediately revoke and rotate the compromised credential at the source provider (e.g., rotating the SMTP password or Postgres credentials) to neutralize the threat. Second, I would use a tool like BFG Repo-Cleaner or `git filter-repo` to systematically scrub the file or string from the entire repository history. Finally, I would force push the cleaned history to the remote and review our `.gitignore` and CI/CD pipelines to ensure automated secret-scanning is implemented to prevent recurrence.
