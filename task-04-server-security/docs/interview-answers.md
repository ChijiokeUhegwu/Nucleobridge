# docs/interview-answers.md

### Hashing

**1. Why should you hash passwords?**
Passwords must be hashed because databases are occasionally breached, and storing plaintext passwords is a catastrophic failure of duty to the user. Users habitually reuse passwords across multiple digital platforms, including banking, email, and corporate accounts. If your database is compromised, a plaintext password leak allows attackers to pivot and compromise the user's entire digital life. Hashing provides a mathematical one-way transformation. When a database is stolen, the attacker receives only the cryptographic representations of the passwords, not the passwords themselves. This acts as a final defensive layer for data at rest, protecting the user's external accounts even after your application's perimeter has been fully breached.

**2. Why use bcrypt instead of SHA-256 for passwords?**
SHA-256 is a message digest algorithm designed explicitly for computational speed and efficiency. Modern GPUs can calculate billions of SHA-256 hashes per second. If an attacker steals a database of SHA-256 hashed passwords, they can brute-force the hashes almost instantly using off-the-shelf hardware. Bcrypt, Argon2, and other adaptive hashing algorithms are designed for the exact opposite purpose: computational cost. They are intentionally slow and memory-hard. By using an adaptive algorithm, you force the attacker to expend massive amounts of CPU time and memory for every single guess. This mathematically bankrupts the attacker's resources, turning a cracking operation that would take hours with SHA-256 into one that takes centuries. 

**3. What is a salt and why do you need it?**
A salt is a cryptographically secure random string of characters generated uniquely for every new password and appended to it before the hashing process occurs. The salt is then stored in plaintext alongside the final hash in the database. Salting solves two critical vulnerabilities. First, it completely neutralizes "rainbow table" attacks, which rely on massive, pre-computed databases of hashes for common passwords. Because every password gets a unique salt, the attacker must compute the hashes from scratch. Second, without a salt, two users with the identical password (e.g., "password123") would generate the exact same hash. An attacker could immediately identify all users sharing passwords simply by scanning the database for duplicate hash strings. 

**4. What salt rounds, or what work factor, should you use? Give a number and defend it.**
Using Argon2id, the optimal work factor is a memory cost of 64MB (`m=65536`), a time cost of 3 iterations (`t=3`), and a parallelism of 4 threads (`p=4`). This specific configuration is defended by direct hardware timing constraints. On a modern server environment, this configuration yields an execution time of approximately 154 milliseconds per hash. In user experience terms, a 154ms delay during a login event is entirely imperceptible to a human being, meaning it costs the business nothing in friction. However, limiting an attacker to roughly 7 guesses per second per core creates an insurmountable financial and temporal barrier for offline brute-force attacks against a stolen database. The work factor scales as hardware improves, keeping the execution time anchored at ~150ms.

**5. You are storing user passwords in a database. Of plain text, SHA-256, AES-256 encryption and adaptive hashing, which is correct and why are the other three wrong?**
Adaptive hashing is the only correct answer. Plain text is wrong because any database breach instantly compromises every user account and their reused passwords elsewhere. AES-256 encryption is wrong because it is a two-way, reversible process requiring a key. If an attacker breaches your server deeply enough to steal the database, they have almost certainly stolen the environment variables containing the AES decryption key, allowing them to decrypt everything instantly. SHA-256 is wrong for a completely different reason: while it is structurally a one-way process (unlike AES), it is vastly too fast. Without an adaptive work factor, an attacker can leverage GPU rigs to guess billions of combinations per second, easily reversing the hashes through sheer brute force.

### Validation

**6. Why is client-side validation not enough?**
Client-side validation is strictly a User Experience (UX) feature, not a security boundary. It exists solely to give honest users immediate, helpful feedback—such as a red border around a malformed email address—without requiring a round-trip network request to the server. However, an attacker does not use your web browser or your frontend React application. They will intercept the API endpoint and send arbitrary HTTP requests directly to the server using tools like cURL or Postman. If validation only exists on the client, the attacker completely bypasses those rules, allowing them to inject malicious payloads, oversized data, or malformed constraints directly into your backend architecture.

**7. What security checks belong in the frontend, and what must the server enforce regardless?**
No true security checks belong in the frontend. The frontend should only enforce UX-oriented formatting constraints: checking if an email looks like an email, ensuring passwords meet length requirements, and verifying that required fields are not empty. This saves the user time. The server, however, must enforce absolutely everything regardless of the frontend. It must rigidly validate the entire shape, length, and format of the incoming data payload using a strict schema. Furthermore, only the server can enforce stateful security constraints, such as verifying session tokens, checking authorization limits (e.g., ensuring a user owns the resource they are trying to edit), and enforcing database uniqueness. 

**8. The user interface hides the delete button for non-administrators. Is that enough? If not, what does an attacker do instead?**
Hiding the UI button is completely insufficient and operates on the fallacy of security through obscurity. An attacker will completely ignore the visual interface. Instead, they will log in as a standard user, monitor the network traffic using browser developer tools or a proxy, identify the REST endpoint used for deletion (e.g., `DELETE /api/users/123`), and manually construct and transmit that HTTP request using their standard user session token. If the server does not explicitly verify that the session token attached to the request belongs to a user with administrative privileges, the server will blindly execute the deletion. Authorization must always be validated at the route handler level, never just by hiding DOM elements.

**9. What is the difference between validation, encoding and sanitisation?**
Validation is the process of inspecting incoming data to ensure it strictly conforms to an expected shape, type, and constraint set (e.g., ensuring an age is an integer between 18 and 99). If it fails, the request is rejected entirely. Sanitisation is the process of actively mutating dangerous input to make it safe, such as stripping `<script>` tags from a blog comment before storing it. Encoding happens at the output stage, translating special characters into a safe format for the destination medium (e.g., translating `<` into `&lt;` before rendering it in an HTML document). Validation blocks bad data, sanitisation alters it, and encoding neutralizes it for display.

**10. Why would you replace the incoming request body with the parsed and validated data rather than leaving both available?**
Replacing the raw incoming request body with the explicitly parsed and validated schema object is a critical defense against Mass Assignment and Prototype Pollution attacks. If both are left available, a developer might accidentally reference `req.body.isAdmin` instead of `validatedData.isAdmin`. An attacker can simply append `"isAdmin": true` to their JSON payload. If the schema validator drops unknown fields but the developer accidentally uses the raw body to update the database, the attacker gains administrative privileges. By completely overwriting or exclusively relying on the statically typed, stripped data object returned by the validator, you guarantee that only the fields you explicitly defined and verified can ever touch your business logic.

**11. Why validate route parameters and query strings, not just the body?**
Route parameters and query strings are entirely user-controlled inputs, making them just as dangerous as the JSON body. A developer might assume that a route like `/api/users/:id` will always receive a numeric ID. However, an attacker can modify the URL to `/api/users/DROP TABLE users` or inject NoSQL operators like `/api/users/?id[$ne]=1`. If these URL parameters are fed directly into a database query or logic flow without strict type coercion and schema validation, they result in devastating SQL injection, NoSQL injection, or application crashes due to unhandled type exceptions. All incoming data, regardless of its transport mechanism, must be treated as hostile.

### Rate limiting

**12. How do you rate limit unauthenticated requests, and what is the problem with the header you would reach for first?**
Unauthenticated requests are typically rate-limited by analyzing the client's IP address. The immediate reflex is to read the `X-Forwarded-For` HTTP header, which proxies and load balancers use to append the original client IP. The critical problem is that HTTP headers can be trivially spoofed by the client. An attacker can inject their own fake `X-Forwarded-For: 12.34.56.78` header into the initial request. If your rate limiter blindly parses the first IP in that header, the attacker can bypass the limit entirely by generating a random IP on every single request. You must configure your reverse proxy to strip client-provided headers and only trust the IP address explicitly appended by your own trusted infrastructure.

**13. Which rate limiting algorithm would you choose for a production API, and what is the boundary burst problem?**
For a production API, the Token Bucket or Sliding Window Log algorithms are superior. The Boundary Burst problem is a fatal flaw in the simpler "Fixed Window" algorithm. In a Fixed Window, if the limit is 100 requests per minute, a user can send 100 requests at 11:59:59, and when the clock strikes 12:00:00, the window resets, allowing them to send another 100 requests at 12:00:01. The server receives 200 requests within a two-second window, completely defeating the purpose of load protection. Sliding Window or Token Bucket algorithms calculate limits based on fluid, rolling timestamps, entirely eliminating the boundary burst vulnerability and ensuring smooth, predictable server load.

**14. Why use a shared store for your counters rather than in-memory counters on each server?**
Production applications operate across multiple horizontally scaled servers placed behind a load balancer. If you use in-memory rate limit counters (like storing a Map in a Node.js process), the counters are completely isolated to that specific server. If a user is limited to 100 requests, they could hit Server A 100 times, and then the load balancer might route their next 100 requests to Server B, effectively doubling their limit. By utilizing a shared, fast-access store like Redis, all server instances query and increment a single, global truth state. This ensures that the rate limit is enforced uniformly across the entire infrastructure footprint, regardless of which instance handles the specific HTTP request.

**15. What HTTP status code should a rate limiter return, and why is 403 the wrong choice?**
A rate limiter must return `429 Too Many Requests`. The `403 Forbidden` status code is the wrong choice because it semantically communicates a permanent authentication or authorization failure—meaning the server understands the request but explicitly refuses to authorize it due to lack of privileges. Rate limiting is not a privilege issue; it is a temporary resource exhaustion issue. The 429 status code accurately communicates to the client architecture that they have simply exceeded their allocated quota. Furthermore, a 429 response allows the server to include a `Retry-After` header, which programmatically informs the client exactly how many seconds they must wait before normal operations can resume. 

**16. What do you do when your rate limit store is unavailable: fail open or fail closed? Answer for your own application specifically.**
For Nucleobridge, a platform built on providing seamless computational bioinformatics experiences, the application must implement a hybrid approach based on liability. If the Redis rate-limit store crashes, general application routes (like running code checks or loading dashboard data) must "fail open." Availability is prioritized over strict quota enforcement to ensure paying users are not locked out of their learning environment due to an infrastructure hiccup. However, authentication endpoints—specifically the login, registration, and password reset routes—must strictly "fail closed." Without a rate limiter, an attacker could utilize the downtime to launch a massive, unthrottled brute-force credential stuffing attack against the authentication boundary, which represents an unacceptable security liability.

### Project Specific

**17. You have two timing numbers for hashing, from your own machine. Walk me through what they mean for an attacker who has stolen your user table.**
On my local hardware, hashing with Argon2id takes 153.720 milliseconds, processing roughly 7 guesses per second. In contrast, SHA-256 executes in 0.892 milliseconds, processing 1,121 guesses per second (scaling into the billions on GPU rigs). If an attacker steals the user table, they must perform an offline brute-force attack on their own hardware. Because I used Argon2id, they are mathematically tethered to the computational gravity of my work factor. They cannot speed it up. Attempting a modest dictionary attack of one billion common passwords against a single user would take them over four years of continuous processing per core. If I had used SHA-256, that same billion-guess attack would be resolved in less than a day. The delay is the defense.

**18. How does a breached password check avoid sending the password anywhere? Explain the mechanism in your own words, then say what the naive version would leak.**
The mechanism utilizes the concept of k-anonymity. When a user types a password, the application hashes it locally using SHA-1. We then slice the hash, taking only the first five characters (the prefix), and send those five characters to the Have I Been Pwned API. The API responds with a massive list of every breached password suffix that shares that five-character prefix. The application then checks locally if our specific suffix is in that downloaded list. The naive version would involve sending the entire plaintext password (or the full hash) directly to the third-party API. This would create a massive security vulnerability, intentionally leaking our users' exact security credentials to an external server outside our jurisdictional control over the network. 

**19. Wrong-answer analysis. Every sentence contains something true. Say what is wrong, in order of severity, and what the candidate has misunderstood about the threat model.**
The most severe failure is the candidate's reliance on SHA-256. While hashing is indeed a one-way function, SHA-256 is built for maximum speed. Even with a unique salt, an attacker with a stolen database can leverage modern GPUs to brute-force billions of combinations per second, rendering the one-way nature irrelevant. Second, the candidate has fundamentally conflated online attacks with offline attacks. They claim that rate-limiting IPs prevents brute force. IP rate-limiting protects the live, online application form credential stuffing. However, hashing is explicitly designed to protect the database *after* it has been stolen and taken offline. Once the database is on the attacker's local machine, network IP rate limits no longer exist. The attacker has unlimited, unthrottled access to crack the hashes.
